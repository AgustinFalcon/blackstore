## Why

Three of the four r2 fixes are in the commit/release and reconcile paths. `applyTerminalFault` on `CONFLICT` GETs the same quadruple and, when the sale is still `COMMIT_PENDING` or `RELEASE_PENDING`, `sameBodyRetries < 1`, and the operation is not retired or blocked, calls `commit` or `release` once more on that quadruple. `commitAndReleaseFollowRecoveryMatrix` now expects `commitAttempts == 2` and `releaseAttempts == 2` for that RESERVED GET, and both arms script PENDING, 409, mismatch, EXPIRED, and 410. `markReconciliationRequired` accepts `COMMIT_PENDING` and `RELEASE_PENDING` and writes the `acceptedPriceVersions` argument. Reconcile posts with `postClientInstance` (`Authorization` + `X-Client-Instance-Id` only). `reconcile-device`, `reconcile-sale`, and `reconcile-op` are gone. `data.present` rows take `clientInstanceId`, `deviceId`, `saleId`, and `operationId` from the envelope or are dropped. Default `application.yml` stays fail-closed.

The GET result is still not applied before that POST. `applyTerminalReceipt` keeps the previous evidence when `receipt.state != expected` (`pending.copy(recoverWithGet = false)`) and `markCommitted` / `markReleased` only flip status. A commit CONFLICT whose GET returns `RELEASED`, or a release CONFLICT whose GET returns `COMMITTED`, stays pending and sends the mutating POST. The technical-spec row says RESERVED, COMMITTED, and RELEASED replace the durable tuple, and the follow-up POST runs only when that stored step is still incomplete. The POST also keeps `pending.evidence.reservationRef`, not the GET ref.

Reserve does not share that POST. `applyReserveFault` GETs and stops. A retryable reserve CONFLICT whose GET is PENDING leaves `recoverWithGet` set, so the next `beginReserve` only calls `recoverReserve`. `StoreCoreRecoveryRehearsalTest` still records one GET and `PENDING_RESERVATION` for that case. r2 asked to stop treating `recoverWithGet` as a GET-only latch when the step is incomplete.

JDBC inbox state is still not the caller's state. `LocalSaleSagaService` passes `receipt.kind.name` and `receipt.state.name`. `JdbcSaleRecordStore.recordInbox` forwards `kind` and then the literal `"PENDING"`, so a COMMITTED, RELEASED, or EXPIRED receipt is stored as inbox `state=PENDING`. `markReserved` still writes `accepted_price_versions = ["price-v1"]`. The connector suite uses `InMemorySaleRecordStore`, which records `INBOX:$kind:$remoteState`, so the green tests do not execute either write.
